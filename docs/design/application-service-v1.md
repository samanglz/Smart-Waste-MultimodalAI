# Application Service V1
## Technical Design Specification

**Status:** Approved for staged implementation
**Version:** 1.0
**Scope:** Backend application orchestration
**Deployment target:** Local Host with Docker
**Storage model:** In-memory for V1

---

## 1. Purpose

The Application Service coordinates the execution of an incoming user
request across the existing application components.

It is responsible for application-level workflow, request lifecycle,
conversation coordination, image registration, idempotency, error
handling, and response construction.

It does not implement Vision, Retrieval, Generation, Final Decision,
or HTTP transport logic.

The Application Service must remain independent of FastAPI and other
transport-specific frameworks.

## 2. Architectural Boundaries

The Application Service coordinates the following independent components:

- ConversationStore
- ImageStore
- ConversationEvidenceRegistryFactory
- PipelineOrchestrator
- RequestExecutionStore
- Trusted actor identity supplied by the backend

The existing PipelineOrchestrator remains unaware of HTTP, ImageStore,
and Application Service implementation details.

ConversationStore, ImageStore, and Evidence Registry remain separate
components with independent responsibilities and lifecycles.

A shared Composition Root will eventually construct and inject the
required implementations.

## 3. Application Command

The transport-independent input is an Application Command.

The command contains:

- request_id: client-generated identifier for one logical operation
- conversation_id: optional identifier of an existing conversation
- question: optional user question, subject to task requirements
- image_bytes: optional encoded image bytes
- media_type: optional supported image media type
- task_type: requested task
- options: RequestOptions
- locale: supported response locale
- actor_id: trusted backend-provided identity

The actor_id must never be accepted as an authoritative identity from
an untrusted client field.

The Application Service generates turn_id and other backend-owned IDs.

The HTTP API must translate its transport request into this command.
AnalyzeRequest is not the public HTTP input contract.

## 4. Request Lifecycle and Idempotency

### 4.1 Identity

The V1 idempotency key is:

    (actor_id, request_id)

The request_id is generated by the client for a new logical operation.
A technical retry must preserve the same request_id.

A deliberate new attempt must use a new request_id.

The backend generates a separate turn_id for each newly accepted user
message.

The conversation_id is generated by the backend when the command does
not specify an existing conversation.

### 4.2 Request Fingerprint

A deterministic fingerprint is computed from all client-controlled
inputs that materially affect execution, including:

- supplied conversation_id, if any
- question
- image SHA-256, if an image is supplied
- image media type
- task_type
- RequestOptions
- locale

The fingerprint must use a deterministic canonical representation.
Dictionary ordering, serialization details, and optional values must
not produce unstable fingerprints.

Generated values such as turn_id, a newly generated conversation_id,
timestamps, and internal request execution IDs are excluded.

The fingerprint is used to detect conflicting reuse of a request_id.
It is not used to merge independent requests with identical content.

If an existing (actor_id, request_id) has a different fingerprint,
the Application Service raises IdempotencyConflictError.

### 4.3 RequestExecution States

The V1 states are:

- PROCESSING
- COMPLETED
- FAILED

These describe request execution, not AnalyzeResponse status.

A valid AnalyzeResponse with status success, partial_success,
needs_clarification, or failed is a completed Pipeline execution.
An unexpected exception is a failed request execution.

### 4.4 Duplicate Request Behavior

For an existing request with the same fingerprint:

- PROCESSING: return the existing processing state; do not execute again.
- COMPLETED: return the previously stored result.
- FAILED: return the previously stored safe failure information.
- Different fingerprint: raise IdempotencyConflictError.

A deliberate retry after FAILED requires a new request_id.

### 4.5 Atomic Reservation

A new request must be atomically reserved in RequestExecutionStore
with PROCESSING status before side effects begin.

Concurrent requests with the same actor_id and request_id must not
both become execution owners.

The reservation operation must atomically distinguish:
- newly reserved request
- duplicate request
- conflicting request

The in-memory implementation must use appropriate synchronization.

### 4.6 RequestExecution Record

The record contains:

- actor_id
- request_id
- conversation_id, once known
- request fingerprint
- execution status
- user turn_id, once created
- AnalyzeResponse result, when available
- safe public error information, when failed
- internal error classification, when failed
- created_at
- completed_at, when finalized

Internal exception details and stack traces must never be exposed
directly to clients.

### 4.7 Restart Behavior

RequestExecutionStore is in-memory in V1.

Backend restart clears all request execution records.
No automatic recovery or re-execution after restart is provided.

ConversationStore and ImageStore are also in-memory and lose their
contents on backend process restart.

## 5. Conversation Lifecycle

### 5.1 Create or Retrieve

If conversation_id is absent, the backend creates a new Conversation
owned by the trusted actor_id.

If conversation_id is supplied, the backend retrieves the Conversation
and verifies ownership and active status.

A conversation is not automatically replaced because the topic changes.

Conversation expiration and TTL are not implemented in V1.
Conversations remain active until explicitly closed or deleted.

### 5.2 History

The Application Service retrieves the existing Conversation history
before appending the current user turn.

The current user message must not be included twice in
AnalyzeRequest.conversation_history.

The current message is supplied through the appropriate current-request
fields. Previous turns are supplied through conversation_history.

The Orchestrator retains responsibility for its existing history
context limits.

### 5.3 User Turn

After input validation, image registration, and successful Conversation
resolution, the Application Service creates and appends the user
ConversationTurn before executing the Pipeline.

The turn contains:
- generated turn_id
- conversation_id
- user role
- user content
- timezone-aware timestamp
- optional image_artifact_id
- other supported existing ConversationTurn fields

If the Pipeline raises an exception, the user turn remains stored.

No assistant error turn is created for a technical exception.

### 5.4 Assistant Turn

Assistant turns are stored only for responses that contain user-facing
content according to this policy:

| AnalyzeResponse status | Assistant turn |
|---|---|
| success | Store the generated answer |
| partial_success | Store useful user-facing content |
| needs_clarification | Store clarification_message |
| failed | Do not store |
| unexpected exception | Do not store |

For needs_clarification, the clarification_message is the content
stored in the assistant turn.

Internal diagnostics, exception text, and Pipeline implementation
details must not be stored as assistant messages.

If assistant turn registration fails, the user turn remains.
Images and Evidence are not automatically deleted.

The Application Service reports the persistence failure and must not
claim that the answer was successfully committed to conversation
history.

## 6. Image Lifecycle and Ownership

### 6.1 Registration

ImageStore remains independent of ConversationStore.

Incoming image bytes are validated and registered using the existing
ImageStore contract.

The returned ImageArtifact is used when constructing AnalyzeRequest.

ImageStore retains the original encoded image bytes and metadata.

### 6.2 Conversation Association

Every registered image used by a Conversation belongs to exactly one
Conversation in V1.

An image may be referenced by multiple turns within that same
Conversation.

ConversationTurn stores only image_artifact_id, not encoded image
bytes.

Cross-conversation image reuse is prohibited.

Application-level ownership checks must be enforced before loading
an image for a request.

### 6.3 Previous Images

Previous images may be used in later requests within the same
Conversation.

Selection must be grounded in the current request and conversation
context.

If the intended image cannot be determined confidently, the system
must request clarification rather than arbitrarily choosing an image.

The current AnalyzeRequest.image contract represents one selected
image. Multi-image Vision execution requires a separate architecture
decision and is not introduced by this specification.

### 6.4 Image Retention on Failure

Once an image is associated with a persisted user turn, Pipeline
failure does not delete the image.

If an image has been registered but no user turn has been committed
and the request fails, cleanup of that unreferenced image is allowed.

After user-turn registration, automatic cleanup on Pipeline failure
or assistant-turn failure is prohibited.

## 7. Conversation Close and Delete

ConversationStore and Evidence Registry remain independent.

Application Service coordinates their lifecycle.

### 7.1 Close

Closing a Conversation must:

1. Verify ownership.
2. Mark the Conversation closed.
3. Close its Evidence Registry.
4. Preserve Conversation history and image data.
5. Reject subsequent requests that attempt to continue the closed
   Conversation.

Closing is explicit. There is no automatic expiration.

### 7.2 Delete

The approved V1 policy is to delete images belonging to the deleted
Conversation.

Deletion must:

1. Verify ownership.
2. Obtain a snapshot of the Conversation and its image references.
3. Prevent new requests from being accepted for the Conversation.
4. Close the Conversation and its Evidence Registry as required.
5. Collect unique image_artifact_id values from all turns.
6. Delete those images from ImageStore.
7. Delete the Evidence Registry and its evidence.
8. Delete the Conversation and all its turns.

An image referenced multiple times within one Conversation is deleted
only once.

Because the stores do not share a transaction, deletion is a
multi-step operation. It must be designed to tolerate partial failure
and repeated cleanup attempts.

Cleanup must be idempotent: deleting an already deleted image or
registry must not corrupt other data.

The implementation must not silently claim complete deletion if one
of the required cleanup steps fails.

A minimal in-memory deletion coordination mechanism may be introduced
if needed to prevent new requests racing with deletion. It must not
turn the stores into a single coupled component.

## 8. Application Request Execution Flow

The intended normal flow is:

1. Validate the command and trusted actor identity.
2. Compute the request fingerprint.
3. Atomically reserve (actor_id, request_id).
4. Return the existing state/result for duplicates.
5. Validate and register a new image, if supplied.
6. Create or retrieve the Conversation.
7. Retrieve previous Conversation history.
8. Create a new user turn, including image_artifact_id if applicable.
9. Append the user turn to ConversationStore.
10. Build AnalyzeRequest using the previous history and current message.
11. Execute PipelineOrchestrator.
12. Evaluate AnalyzeResponse and append an assistant turn only when
    permitted.
13. Store the final RequestExecution result and mark COMPLETED.
14. Return an Application Result.

The exact placement of Conversation creation and image registration
must preserve the following invariants:

- Invalid input must not create a Conversation or user turn.
- An invalid image must not create a Conversation.
- A successfully registered image that is not yet referenced by a
  committed user turn may be cleaned up after failure.
- A committed user turn is not removed when Pipeline execution fails.
- A new Conversation created for an accepted user turn is retained
  after Pipeline failure and its conversation_id remains available
  to the client.
- A duplicate request must be detected before repeating side effects.

## 9. Failure Semantics

| Failure point | Required behavior |
|---|---|
| Initial command validation | No new turn; no Pipeline execution |
| Fingerprint conflict | Reject; no side effects |
| Request reservation conflict | Do not execute Pipeline |
| Image validation/registration | No user turn; no Conversation creation for invalid image |
| Conversation ownership failure | No user turn; no Pipeline execution |
| User turn append failure | Do not execute Pipeline |
| Pipeline exception | Keep user turn and associated image; no assistant turn; mark execution FAILED |
| Pipeline returns failed | Keep user turn; no assistant turn; store response; mark execution COMPLETED |
| Assistant turn append failure | Keep user turn, image, and Evidence; mark execution failure and report persistence error |
| Request finalization failure | Do not report successful completion unless the final state is confirmed |

The system must distinguish a valid failed AnalyzeResponse from an
unexpected execution exception.

The stores are not transactional together. The implementation must
document and test partial-failure behavior rather than claiming
cross-store atomicity.

## 10. Application Result

The Application Service returns a transport-independent result.

It should contain the information required by API clients, including:

- request_id
- conversation_id
- request execution state
- AnalyzeResponse when available
- safe error code and message when failed
- whether the result was retrieved from an existing execution

The API is responsible for mapping this result to HTTP status codes
and response schemas.

A duplicate PROCESSING request must be representable without
pretending that a final AnalyzeResponse exists.

## 11. Dependency Injection and Composition Root

The Application Service receives its dependencies through
constructor injection.

Expected dependencies include:

- ConversationStore
- ImageStore
- PipelineOrchestrator
- ConversationEvidenceRegistryFactory
- RequestExecutionStore
- ID generation abstraction if needed
- clock abstraction if needed

The same in-memory store instances must be shared across the
application lifetime.

The Evidence Registry Factory must be shared so evidence remains
available across requests for the same Conversation.

The Application Service must not instantiate ONNX sessions, Gemini
clients, retrieval indexes, or FastAPI application objects.

The Composition Root owns concrete adapter construction and
dependency wiring.

## 12. Testing Strategy

### Unit tests

- Application command validation
- deterministic fingerprint calculation
- RequestExecutionStore reservation and concurrency
- duplicate and conflicting request behavior
- state transitions
- safe versus internal error representation
- assistant turn eligibility
- image association validation
- Conversation lifecycle coordination
- deletion idempotency

### Integration tests

Tests must exercise the real coordination between:

- Application Service
- InMemoryConversationStore
- InMemoryImageStore
- InMemoryImageLoader
- Evidence Registry Factory
- PipelineOrchestrator or a controlled test implementation

They must verify end-to-end state changes, not only isolated mocks.

Required scenarios include:

- first request creates a Conversation
- subsequent request continues the same Conversation
- user turn is registered before Pipeline execution
- current message is not duplicated in history
- image registration and turn association
- previous image selection and ownership checks
- Pipeline exception preserves user turn and image
- failed AnalyzeResponse creates no assistant turn
- clarification response creates assistant turn
- assistant persistence failure preserves user turn and evidence
- duplicate request does not execute Pipeline again
- concurrent duplicate requests have one execution owner
- fingerprint conflict is rejected
- Conversation close prevents continuation
- Conversation delete removes owned images and evidence
- partial deletion can be retried safely

## 13. Explicit V1 Non-Goals

The following are not included:

- persistent database storage
- automatic Conversation TTL or expiration
- automatic recovery after backend restart
- distributed locks or distributed transactions
- background job infrastructure
- automatic retry of failed Pipeline executions
- cross-conversation image sharing
- multi-image Vision execution in one AnalyzeRequest
- frontend implementation
- changes to existing Retrieval or Query Rewriting architecture

## 14. Implementation Sequence

Implementation must proceed in independently reviewed stages:

1. Finalize and create this technical design.
2. Extend ConversationTurn with optional image_artifact_id.
3. Implement RequestExecution contracts and errors.
4. Implement InMemoryRequestExecutionStore.
5. Add and run focused unit tests.
6. Design and implement application-level Conversation and image
   coordination.
7. Implement Application Service.
8. Add integration tests for complete workflows and failure semantics.
9. Implement API schemas and endpoints.
10. Implement Composition Root and dependency wiring.
11. Validate the real ONNX execution path.
12. Build and verify Docker deployment on the local Host.

Each implementation, inspection, test, or dependency-installation stage
requires its own explicit approval.

No existing project outside smart-waste-multimodal-ai may be modified.
The frontend remains postponed until backend implementation is
complete.
